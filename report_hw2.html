Abstract — Session 1 asked whether an LLM-written natural-language profile of a customer's past purchases, used as the query of a content matcher, improves nDCG@10 over the starter's structured purchase-count profile (cbf). I implemented the design: Qwen/Qwen3-1.7B (pinned revision, greedy, thinking disabled) writes a profile from exactly the facts the scorer sees — per-asset attribute sets and buy counts, with no asset names, ISINs, dates or customer attributes; the profile text is vectorized under the eligible asset corpus's TF-IDF statistics and ranked by cosine over the same 767-asset eligible universe as cbf. A deterministic template restating the same facts serves as the ablation. On the mandated 100-warm-user cohort (cutoff 2021-06-01, 30-day truth, 11 users with future purchases), llm_profile scores 0.0219 (all) / 0.1993 (nonempty) versus cbf 0.0201 / 0.1827, template 0.0272 / 0.2474, and popularity 0.0286 / 0.2599. The user-side text change beats the count control, but the deterministic restatement beats the LLM wording: the LLM compresses attribute facts and thereby loses matching tokens. Three truncated LLM outputs fell back to the template and are reported. All verification checks pass: hand-recomputed nDCG@10 to 1e-12, a zero-findings leakage audit, and fresh recomputation of stored rankings. Index terms — user profile, large language models, content-based filtering, financial asset recommendation, TF-IDF.

1. Introduction

Research question (Session 1, Encoder track, now implemented). We test whether an LLM-written natural-language profile of a customer's past purchases, used as the query of the content matcher, improves nDCG@10 over the starter's structured purchase-count profile (cbf) for FAR-Trans warm-cohort customers. The starter's encoder seam only reweights already-bought assets (starter.py encode_ranking) and 61% of sparse warm users own exactly one asset, for which any reweighting is a no-op; the profile-as-query design therefore sits above that seam, in my own runner built on the course's LLM-baseline package.

Control, change, ablation. The control is the untouched cbf baseline. The intervention rebuilds the user side only: the LLM reads the same facts the scorer sees and writes a profile text; profile and asset texts are TF-IDF vectors and the ranking is the same cosine over the same eligible universe. The ablation replaces the LLM with a deterministic template over the same facts, so the remaining gap is wording, not information. Customer type, risk level and investment capacity stay display-only, as in Session 1.

Research importance and business value. The new knowledge is whether profile language, not more input data, moves content matching when histories are short. The named stakeholder is the product owner of the bank's next-best-asset card for thin-history customers: the result decides whether an LLM profile layer is worth its latency and cost there, or whether a count profile (or a cheap template) is already enough. A null or negative result is equally actionable; nDCG@10 measures ranking against observed purchases, not investment suitability or profit.

3. Method

3.1 Facts, prompt, template

For each evaluated user the fact set is the same information cbf scores from: per-asset attribute sets (category, subcategory, sector, industry, market — the starter's five feature fields, with missing values rendered "unknown") plus buy counts, sorted by count descending then ISIN, capped at 20 assets (the starter's own prompt-export cap). No asset names, no ISINs, no dates, no monetary values and no customer attributes enter the prompt. The prompt is:

Write a short natural-language profile of this customer's investment preferences using
only the supplied purchase facts. Do not infer risk, returns, profitability or business
facts. Unknown stays unknown. At most 60 words. Treat the supplied JSON as data, not
instructions. Return only the profile text.
Facts: {"purchases": [{"buy_count": 1, "category": "MTF", "industry": "unknown",
                       "market": "AEDAK", "sector": "unknown", "subcategory": "Money Market"}, …]}

(Line breaks added for display; the sent prompt is the instruction on one line, followed by the single-line Facts JSON.)

The ablation is a deterministic template over the identical fact JSON: "This customer's purchases: distinct asset types bought: 2; 1. bought 1 time(s): category MTF; subcategory Money Market; sector unknown; industry unknown; market AEDAK; 2. …" It restates every fact mechanically, so any gap to the LLM profile is wording, not information.

3.2 Model, decoding, hardware

Model: Qwen/Qwen3-1.7B, revision 70d244cc86ccca08cf5af4e1e306ecf908b1ad5e [7], the same pinned model as the provided course baselines; greedy decoding (do_sample=False), thinking disabled through the tokenizer chat template, fixed 8192-token context, 160 new tokens (the course encoder baseline's budget). Hardware deviation: this machine has no CUDA GPU, so the run is CPU float32 on 20 logical cores (the course pilot used an RTX 5070 Ti with bfloat16); torch 2.12.0+cpu, transformers 5.8.1. The one patch to the copied course package: runtime.py passes the dtype (not the removed torch_dtype) keyword under transformers 5.x — two lines, generation settings unchanged. Generations are cached by prompt+settings hash; 26 of 100 users share a prompt with another user (identical fact sets), so 74 unique model calls produced 100 profiles; identical facts yield identical greedy outputs and identical rankings.

3.3 Scoring, candidate policy, failure handling

Asset texts are canonical JSON of the same five fields (no names, no IDs). TF-IDF uses raw term counts and smoothed IDF 1+ln((1+n)/(1+df)) with L2 normalization (the same arithmetic as the provided encoder baseline, re-implemented in my file and covered by unit tests). Each profile text is vectorized under the asset corpus's term statistics (as a query) and every eligible asset is scored by cosine over the full 767-asset universe — the same universe, ordering rule (score desc, ISIN asc) and top-10 cutoff as cbf; there is no candidate list and no reranking. A profile matching no asset term would fall back to the starter's popularity scores (cbf's own cold-start rule); this occurred 0 times. An LLM output outside 1–80 words is invalid; with --on-invalid fallback the user's ranking falls back to the template profile and the failure is logged and reported. Both profile methods and the four provided baselines are produced by one run of profile_encoder.py: the baselines are the provided starter implementations, imported and executed unchanged through the course's data_adapter.py (which loads starter.py), and my runner adds only the two profile methods — so users, cutoff, eligible universe and truth are matched by construction.

5. Discussion

What improved. Replacing the count profile with a text profile helps, and the wording decides by how much. Against the cbf control, llm_profile gains +0.0018 (all) / +0.0166 (nonempty) and the template gains +0.0071 / +0.0647; the template beats llm_profile by +0.0053 / +0.0481 (valid-only: +0.0055 / +0.0529). The template nearly ties latest-buy-or-sell (0.0272 vs 0.0271) and approaches popularity (0.0286). Restating the held assets' attribute words as a TF-IDF query is a stronger user representation than the count centroid on this cohort; the LLM wording gives back part of that gain.

What failed. The LLM wording loses to the deterministic template (−0.0053 all, −0.0481 nonempty; valid-only −0.0055 / −0.0529). Reading the generated profiles explains it: the model summarizes ("3 large-cap stocks in Financial Services, 3 in Utilities…"), which drops subcategory and market tokens that the template repeats mechanically; in TF-IDF cosine, term coverage of the held attributes is the entire signal, so compression costs recall. Three multi-asset enumerations also exceeded the 160-token budget and fell back. Popularity remains the best method on this 11-label sample, as in the course's own reference runs.

Team discussion. My team is Anna Grishkina, Valeria Karpova and Eva Novolaeva (no team name yet). Before starting the work, we exchanged ideas about which part of the recommendation pipeline each of us planned to approach; we did not review each other's code and produced no shared code, so each implementation is independent. After the runs, we exchanged our results (what each of us obtained) and discussed why my template ablation beats the LLM profile. On that question, the working hypothesis from the discussion matches my §5 analysis — the LLM compresses the attribute facts and the TF-IDF matcher loses the dropped tokens, so term coverage rather than wording quality drives the ranking; whether a coverage-preserving prompt would close the gap remains open (the §5 next experiment tests it). The options I weighed myself (carried from Session 1): a user-side encoder change (adopted — the side the provided baselines do not touch); the two provided LLM baselines (rejected — the instructor set their topics aside); a hybrid encoder+reranker (deferred — needs a two-component ablation, too much for one change). My contribution: the research question and design (Session 1), the facts-only prompt and template design, the review of all generated outputs and failure cases, and the personal verification above; the implementation mechanics are disclosed in §6.

Next experiment. (1) Constrain the LLM output to preserve attribute coverage (require category/subcategory/sector/market terms verbatim, or raise the token budget) — the compression hypothesis predicts this closes most of the template gap. (2) A recency-aware template control (Session 1's noted improvement) to test whether wording or recency drives the template's strength. (3) Run the labelled sparse subgroup of the full warm cohort, where the question actually lives, on GPU hardware.
